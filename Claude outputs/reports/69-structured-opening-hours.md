## 1. Edit before approve, for every field

This is the part you needed today, and it is done.

The review screen now has **Edit fields before approving**, listing every field the submission
carries. Correct any of them in place and approve; the corrected value goes onto the bar and
`bar_submissions` keeps what the owner sent, untouched, so we can always show them their own
words.

Fields it covers: name, city, country, type, address, opening hours, website, Instagram,
phone, email. The description keeps the task 66 panel it already had.

It also flags characters we do not publish, before they land, rather than after.

### The Prophecy worked example, verified end to end

I ran the real submission text through the real screen:

| | |

| Arrives as | `Sunday to Thursday — 4:00pm to 1:00am Friday & Saturday — 4:00pm to 2:00am` |

Only the field that changed is sent. With nothing edited the request carries no `overrides`
key at all, which is byte-for-byte the behaviour before this task, so ignoring the panel
changes nothing.

**This can ship on its own.** It does not depend on the structured hours below.

## 2. Structured hours in the owner form

The form never had an hours field at all. It has one now: seven rows, an open and a close
time per day, and a Closed toggle. There is nowhere to type a dash.

Verified in the browser at both widths:

| | 390px | 1440px |
|---|---|---|
| Rows | 7 | 7 |
| Row height | 66px | 41px |
| Day label | `Mon` | `Monday` |
| Horizontal overflow | none | none |

On the phone the row drops to a 44px day column plus the times, and the Closed toggle moves
under them rather than competing for width. That was the constraint that shaped the layout,
and I checked it there first as the guard asked.

Live preview, built by filling the form as Prophecy:

> **Will show as:** Mon-Thu 16:00-01:00, Fri-Sat 16:00-02:00, Sun closed

Plain hyphens, generated by us, identical every time. Six "next day" badges appeared on the
past-midnight rows, which is the normal case for a bar and is shown rather than rejected.

**A bug I introduced and caught:** on a half-filled form the preview read
`Daily undefined-undefined`. A day that is open but has no times yet is half-filled, not a
statement, so it is now left out of the preview entirely and an empty form previews nothing.

### The column

`scripts/structured-hours-migration.sql`, **not yet run**, needs your hand in the SQL editor.
It adds `bars.opening_hours_structured` (jsonb), and both `opening_hours` and
`opening_hours_structured` to `bar_submissions`, which has **no hours column of any kind**
today. The free-text column stays as the display source for every bar that has one.

### The parse rate, over the real corpus

| | |
|---|---|
| Active bars | 1,506 |
| With hours | **1,097** |
| Parse cleanly into the structured shape | **793 (72.3%)** |
| Would need a human | **304 (27.7%)** |

The 304 are not badly written, they are **prose rather than data**, and that is why I would
be cautious about a later migration pass:

- `Daily 6pm till late` — no close time exists
- `Tue-Sun evenings (booking by introduction)` — no times at all
- `Daily 5pm-1:30am; Sunday brunch 12:30-5pm (21+)` — two sessions in one day, which the
  structure does not model
- `Mon-Thu & Sun 4pm-3am, Fri-Sat 4pm-5am (lounge Thu-Sat from 7pm)` — a second room

A migration would either lose that information or invent times nobody supplied. My
recommendation, for when you decide: migrate the 793 and leave the 304 as free text
permanently, rather than forcing them.

One thing to weigh: of the 793 that parse, only 61 regenerate byte-identical, because the
canonical output is 24h and many originals are written `4pm-3am`. `format-hours.ts` already
converts per country at render time, so this affects storage rather than what a visitor sees,
but a migration would visibly rewrite the stored string for roughly 730 bars.

## 3. What "Open now" and the schema would take

Not built, as instructed. What each needs, now that the column exists:

**"Open now" on a card.** A pure function taking the structured week, the bar's IANA timezone
and the current instant, returning open/closed/closing-soon. The work is not the function,
it is that **`bars` has no timezone column**: we have country and coordinates but not a zone,
so a timezone lookup or column comes first. Past-midnight also means "is it open at 01:30 on
Saturday" has to check Friday's row, which the `close <= open` convention already encodes.
Then a badge on the card and a filter chip beside the type chips. Half a day, most of it the
timezone.

**`openingHoursSpecification`.** Small, and it only works on structured rows.
`SCHEMA_DAY` is already exported for it. Each day becomes
`{"@type":"OpeningHoursSpecification","dayOfWeek":"Monday","opens":"16:00","closes":"01:00"}`,
emitted in the bar profile's existing JSON-LD block, and omitted entirely for rows with only
free text rather than guessed at. An hour, and it is the one Google actually reads.

## 4. The two em dashes: fixed, and a correction

Both fixed in place, by id:

| | Before | After |
|---|---|---|
| `isa-cocteleria` | `Daily 7pm-1am (temporarily closed — reopens 3 Sep 2026)` | `... (temporarily closed, reopens 3 Sep 2026)` |
| `punch-room-at-edition-rome` | `Temporarily closed (summer 2026) — check the hotel for reopening` | `Temporarily closed (summer 2026), check the hotel for reopening` |

No global rewrite was run. But two things in the task are not right, and they matter:

**Prophecy's hours do not contain em dashes.** The stored value is
`Sun–Thu 16:00–01:00, Fri–Sat 16:00–02:00`, which uses **en dashes** (–), not em dashes (—).
Prophecy is also already a live bar, not a pending submission; there is no Prophecy row in
`bar_submissions` at all.

**154 active bars use en dashes in their hours.** That is the real format inconsistency:
roughly 154 write `Sun–Thu 16:00–01:00` and roughly 940 write `Mon-Thu 5pm-12am`. An en dash
in a numeric range is conventional typography rather than a house-rule breach, which is why
the em-dash rule did not catch it and why I have not touched them. If you want one convention
across all 1,097, say so and it is a separate pass. Structured hours fix it going forward
regardless, because the generator only ever emits a plain hyphen.

## 5. Archive: the task named the wrong file

**The task asks for `action === 'archive'` in `src/app/api/admin/submissions/route.ts`. That
route operates on `bar_submissions`, and building it there would have shipped broken.**

The evidence:

- `scripts/archive-status-migration.sql` widens the status constraint on **`owner_submissions`**, a
  different table. `bar_submissions` has no `archived` in its constraint, so the write would
  have failed.
- `bar_submissions` has no `submitted_data` column, which the task says archiving keeps intact.
- The archived tab the task says "is already in the admin filter row" is on
  `/admin/owner-edits`, not `/admin/submissions`.
- Photos come from owners through `owner_submissions`. `bar_submissions` is the public
  add-your-bar inbox, which carries one `photo_url`, not several.

Everything the task describes is true of **owner edits**. So I built it there:

- `action === 'archive'` in `src/app/api/admin/owner-submissions/route.ts`, setting
  `status: 'archived'`, keeping `submitted_data`, sending nothing to the owner.
- An **Archive** button on the submission card between Approve and Reject. Reject stays.

### What the owner sees, per status

Checked, not assumed. `src/app/api/owner/bars/route.ts` already filters `.neq('status', 'archived')`,
so **archived rows are already invisible to owners**, which is what you wanted and it needed
no change. Pending and rejected show as they did.

### Publishing a photo from an archived row

**No, not today.** The photo picker is gated on `sub.status === 'pending'` and on the
submission exceeding the tier's photo limit, so the moment a row is archived the picker
disappears and the photos, while still in `submitted_data`, cannot be published from the
screen.

What it would take: relax that gate to include `archived`, and add an action that applies
selected photos without flipping the row to approved, so archiving stays a shelf rather than
becoming a slow approve. Perhaps two hours. Worth doing if the point is to come back to
these photos, because right now archiving them means they can only be recovered by hand.
